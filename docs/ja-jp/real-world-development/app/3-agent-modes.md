最初にプロジェクトへ小さな機能を追加しました。しかし、より大きな変更には、さらに堅牢なプロセスが必要です。GitHub Copilot app は組織の既存のフローに沿って作業できるように設計されており、適切なものを適切な方法で構築できます。このレッスンから数回にわたり、一般的なエージェント主導の開発プロセスを実践します。Issue から新機能を作成し、コードと機能を検証して、最終的にプロジェクトへマージします。

> [!NOTE]
> 機能のワークフローを続ける間は、同じセッションを使用します。通常は作業対象のファイルの種類ごとに異なるセッションや PR を使用しますが、ここでは中心的な概念に集中できるよう手順を短縮します。

このレッスンでは、次の内容を学びます。

- GitHub Issue から新しいエージェントセッションを開始する。
- **Plan** モードで要件を定義する。
- **Autopilot** モードを使用して新機能を実装する。
- コードをレビューする。
- ブラウザーキャンバスで機能を手動検証する。

この機能の作業を続けながら、リポジトリの指示を更新し、既存の quality-checks スキルをカスタマイズして、MCP による検証を追加し、QA エージェントを作成して、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが充実し、訪問者がゲームをカテゴリーとパブリッシャーで絞り込める機能が必要になりました。バックログの Issue に機能は記載されていますが、カテゴリーの組み合わせ方など、コーディング前に合意すべき詳細があります。Plan モードで決定事項を整理してから、範囲を限定した実装を Autopilot に許可します。

## 背景

AI コーディングエージェントを開発フローに導入しても、基本は変わりません。むしろ、基本はさらに重要になります。多くの開発者は、次のような流れで作業します。

1. 必要な作業の詳細が記載された Issue を開く。
2. 構築する内容の計画を作成する。
3. コードを構築してレビューする。
4. テストを実行してコードを検証する。
5. 新機能を手動で検証する。
6. pull request (PR) を作成する。
7. コードレビューと継続的インテグレーションプロセスが成功したら、コードをマージする。

> [!NOTE]
> 正確な手順はチームや組織によって異なりますが、多くの場合は上記の流れを調整したものです。

この標準的なアプローチを守ることで、AI が生成したコードが定められた要件を満たし、人が作成したコードと同じ審査プロセスを通るようにできます。

## セッションモード

**セッションモード**は、エージェントの自律性を制御します。プロンプトフィールドの下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive**: 開発者とエージェントが共同で作業します。エージェントは変更を提案し、続行前に入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントが自律的に作業し、入力を待たずにコードの作成、テストの実行、反復を行います。

まず Plan モードで計画をレビューし、その後 Autopilot で実装します。

## Issue からセッションを開始する

星評価の PR がマージされ、ローカルの `main` が最新であることを確認してから、新しいセッションを開始します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリフォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選択します。既存の **Allow users to filter games by category and publisher** Issue を開きます。用意された Issue を使うため、作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選択します。

    ![GitHub Copilot app の Issue ビューで、New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モードセレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` の実行を依頼します。ターミナルでは動作するのにセッションでは見つからない場合は、アプリの PATH またはバージョンマネージャーの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで npm を再インストールしないでください。

## フィルター機能を計画する

計画を立てると、Copilot がコードを書く前にアプローチをレビューできます。Issue から開始したため、Copilot は機能のリクエストをコンテキストとして把握しています。計画を作成するには、次の手順を行います。

1. 次のプロンプトを送信します。

   ```plaintext
   Build this feature.
   ```

2. Copilot の質問に回答し、計画を Issue の受け入れ条件と照らし合わせます。カテゴリーとパブリッシャーによる絞り込み、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認します。
3. 複数のカテゴリーをどう組み合わせるか、一致するゲームがない場合にどうするかなど、不明確な動作について話し合います。
4. プロジェクトの既存ツールを使った lint、単体テスト、E2E テスト、型チェックが計画に含まれていることを確認します。計画はフィルター機能の実装とテストに絞り、PR は品質ワークフローの完了後に作成します。
5. 必要であれば計画の変更を依頼し、納得してから承認します。後で検証できるよう、Issue の URL と合意した追加の取り決めを記録します。

## Autopilot を明示的に承認する

実装を開始する前に計画をレビューし、セッションが Autopilot モードで動作することを確認します。

1. 計画に納得したら、**Approve and implement this plan**、または使用中のバージョンに表示される同等のオプションを選択します。
2. モード表示を確認し、**Autopilot** になっていることを確かめます。承認によってモードが自動的に切り替わるとは限りません。

Copilot は実装を開始し、計画に沿ってコードを生成し、テストを実行しながら作業を反復します。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があるため、先に計画をレビューしてください。依存関係の不足やポート競合が報告された場合は、チェックを完了と判断する前にセットアップの問題を解決します。停止してよいのは、自分で起動したサーバーだけです。

## 実装をレビューして検証する

生成されたコードも、他のコードと同じようにマージ前にレビューします。実装とテストを確認し、チェック結果を調べてください。

1. **Changes** を開き、フィルター機能の実装とテストを確認します。
2. 複数カテゴリーとパブリッシャーの組み合わせも含め、結果を Issue と承認した追加の取り決めに照らし合わせます。変更が既存のリポジトリの指示に従っていることも確認します。
3. lint、単体テスト、E2E テスト、型チェックの出力を確認します。スキップされたチェックは成功ではありません。
4. 実装を受け入れる前に失敗を解消し、該当するチェックを再実行します。Playwright の E2E 設定はビルドしてプレビューを配信し、ローカルサーバーを再利用できます。テスト対象が以前のレッスンではなく、この worktree のサーバーであることを確認します。

## 新機能を確認する

ブラウザーキャンバスでサイトを開き、フィルターが期待どおりに動作することを確認します。

1. 次のプロンプトを使い、アプリを起動してブラウザーキャンバスでページを開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. アプリが起動し、Copilot app 内にブラウザーウィンドウが開くまで待ちます。
3. カテゴリーを選択し、結果がそのカテゴリーに一致することを確認します。フィルターを解除してからパブリッシャーを選択し、結果がそのパブリッシャーに一致することを確認します。
4. カテゴリーとパブリッシャーのフィルターを組み合わせ、結果を Issue と承認済みの計画に照らし合わせます。複数カテゴリーがサポートされる場合は、合意した組み合わせ方を確認します。
5. 一致するゲームがない組み合わせを試し、空の状態を確認します。フィルターを解除またはリセットし、一覧全体が戻ることを確認します。
6. 確認が終わったら、次のプロンプトを使い、このセッションで起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンに向けてセッションを保持する

フィルター機能の PR はまだ作成またはマージしません。レッスン 4 から 8 では同じセッション、worktree、ブランチを使用します。次はカスタム指示をフィルター機能のコードに適用し、その後スキルと QA の改善を加えてから、レッスン 8 でまとめた PR を作成してマージします。開発サーバーを停止した後は、セッションをアイドル状態にしておき、次のレッスンで同じセッションに戻ります。

## まとめと次のステップ

このレッスンでは、異なるエージェントモードを使って機能を構築し、レビューしました。

- GitHub Issue から新しいエージェントセッションを開始した。
- **Plan** モードで要件を定義した。
- **Autopilot** モードを使用して新機能を実装した。
- コードをレビューした。
- ブラウザーキャンバスで機能を手動検証した。

次は、[カスタム指示を使用して][next-lesson]、コードが文書化されたプラクティスに従うようにする方法を確認します。
